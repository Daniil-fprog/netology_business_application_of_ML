### Описание и назначение

Модель персонализирует выдачу вин для зарегистрированного пользователя. Она
оценивает, насколько каждое доступное вино похоже на вина, которые пользователь
ранее отметил лайком. Полученная оценка сходства объединяется с базовым
неперсонализированным рейтингом товара.

Решаемая задача — **ранжирование**: после применения обязательных параметров
фильтрации модель должна поднять выше вина, которые лучше
соответствуют его истории предпочтений.

Это самописная content-based рекомендательная модель на Python без внешних
ML-фреймворков. Она не является нейросетью и не использует готовую обучаемую
модель из `scikit-learn`. Под «обучением» понимается построение векторов вин и
пользовательских профилей; оптимизация функции потерь по градиенту не
выполняется.

## 2. Model Parameters — параметры модели

### Архитектура и алгоритм

Каждое вино преобразуется в разреженный вектор числовых и категориальных
признаков. Категория кодируется отдельным ключом, например `color:red` или
`country:italy`.

| Признак | Преобразование или вес |
|---|---:|
| Цена | `price / max_price_in_catalog` |
| Рейтинг | `rating / 5` |
| Цвет | 2.0 |
| Тип сахара | 2.0 |
| Сорт винограда | 1.5 |
| Страна | 1.0 |
| Бренд | 0.75 |

После формирования вектор вина нормализуется по L2-норме. Профиль пользователя
строится как среднее арифметическое векторов понравившихся вин с повторной
L2-нормализацией:

```text
user_profile = normalize(mean(vectors_of_liked_wines))
```

Персональная оценка равна косинусному сходству профиля и вина. Поскольку оба
вектора нормализованы, она рассчитывается скалярным произведением:

```text
ml_score(user, wine) = dot(user_profile, wine_vector)
```

Итоговый score объединяет ML-оценку с базовым ранжированием:

```text
final_score = 0.35 * standard_score + 0.65 * ml_score

standard_score = 0.55 * rating
               + 0.25 * price_fit
               + 0.20 * popularity
               + preference_bonus
```

Доля персонализации настраивается переменной `ML_PERSONALIZATION_WEIGHT`, а веса
базового ranking — переменными `RANKING_*`.

### Данные для обучения

Модель получает из PostgreSQL:

1. Каталог доступных вин:
   - `wine_id`;
   - цену;
   - внешний рейтинг;
   - цвет;
   - тип сахара;
   - страну;
   - бренд;
   - сорта винограда.
2. Историю положительной обратной связи в формате
   `user_id -> множество wine_id`, сформированную по лайкам.

В учебном сценарии используются локальные mock-данные. Согласно README, они
содержат 100 вин, 20 пользователей и 120 лайков. Способ формирования мока не
гарантирует соответствия распределению реальных пользователей и товаров.

Чувствительные демографические признаки напрямую не используются. При этом
идентификатор пользователя и история его предпочтений являются данными, которые
требуют контроля доступа.

### Данные для оценки

Отдельный зафиксированный evaluation-датасет в текущей версии отсутствует.
Имеются небольшие синтетические примеры в unit- и integration-тестах. Они
проверяют логику программы, но не репрезентативны для оценки качества
рекомендаций в эксплуатации.

Для будущей offline-оценки взаимодействия следует делить по времени: ранние
лайки использовать для построения профиля, а последующие — как тестовый набор.
Такой подход предотвращает утечку будущих действий пользователя в обучение.

### Формат входа

При построении модели:

- список объектов `WineCandidate`;
- словарь `dict[int, set[int]]`, сопоставляющий пользователю понравившиеся вина.

При инференсе:

- `user_id`;
- список `wine_id` кандидатов, которые прошли фильтры по параметрам формы.

Структурированные параметры формы напрямую в ML-вектор не входят. Они задают
жёсткие фильтры по цвету, типу сахара, диапазону цены и минимальному рейтингу.

### Формат выхода

Метод `scores()` возвращает словарь `wine_id -> ml_score` либо `None`, если
профиль пользователя не найден. Для используемых неотрицательных признаков
`ml_score` лежит в диапазоне от 0 до 1: большее значение означает большее
сходство с ранее понравившимися винами.

Внешний API возвращает итоговый `score`, TOP-N карточек вин и режим работы
`recommendation_mode`: `ml` или `standard`.

### Обучение и эксплуатация

Модель строится:

- при старте приложения, если `ML_TRAIN_ON_STARTUP=true`;
- вручную через endpoint `POST /ml/retrain`.

Векторы и профили сохраняются только в оперативной памяти экземпляра API. Новые
лайки не обновляют профиль автоматически — для их учёта требуется повторное
обучение. При отсутствии профиля сервис использует стандартное ранжирование.

## 3. Quantitative Analysis — количественная оценка

### Текущее состояние

В проекте пока отсутствуют выделенный контрольный датасет, offline-эксперимент и
измеренные значения качества рекомендательной системы. Поэтому заявлять
достигнутые `Precision`, `Recall` или бизнес-эффект нельзя.

Функциональные автотесты проверяют следующие свойства:

- похожее вино получает больший score, чем отличающееся;
- ранее понравившееся вино исключается из персональной выдачи;
- пользователь без лайков получает standard ranking;
- результаты сортируются по score и ограничиваются TOP-N;
- фильтры по цене, цвету, сахару и рейтингу применяются корректно.

При локальной проверке командой
`python3 -m pytest tests/unit/test_ml_recommender.py tests/unit/test_recommendation.py -q`
успешно пройдено 7 тестов. Это подтверждает корректность реализации проверяемых
сценариев, но не является измерением рекомендательного качества.

### Метрики для последующей оценки

| Метрика | Назначение | Текущее значение |
|---|---|---|
| `NDCG@5` | качество порядка релевантных объектов в TOP-5 | не измерено |
| `Precision@5` | доля релевантных объектов среди пяти рекомендаций | не измерено |
| `Recall@5` | доля релевантных объектов, попавших в TOP-5 | не измерено |
| `HitRate@5` | наличие хотя бы одного релевантного объекта в TOP-5 | не измерено |
| Catalog coverage | доля каталога, появляющаяся в рекомендациях | не измерено |
| CTR / like conversion | реакция пользователей на рекомендации | не измерено |

Основной offline-метрикой предлагается сделать `NDCG@5`, потому что API по
умолчанию возвращает пять рекомендаций и порядок карточек влияет на результат.
В production её необходимо дополнять online A/B-тестом против standard ranking.

### Факторы и срезы анализа

Качество следует рассчитывать отдельно:

- для пользователей с разным количеством лайков;
- для разных ценовых диапазонов;
- по цвету и типу сахара;
- для популярных и редких стран, брендов и сортов винограда;
- для полных и неполных карточек товара;
- для режима ML и fallback-режима.

Графики и результаты анализа по срезам пока отсутствуют, поскольку evaluation-
набор и соответствующий pipeline ещё не реализованы.

## 4. Considerations — условия применения

### Предполагаемые пользователи

- посетители сервиса подбора вина;
- backend-приложение, вызывающее модель при `POST /recommendations`;
- разработчики и администраторы, запускающие переобучение и мониторинг.

### Предполагаемые сценарии использования

- формирование персонального TOP-N вин по структурированным параметрам фильтрации;
- повышение в выдаче вин, похожих на ранее понравившиеся;
- исключение уже понравившихся товаров из персональной выдачи;
- fallback на standard ranking для новых пользователей.

До применения модели бизнес-правила фильтруют каталог по явным требованиям
пользователя. Модель ранжирует только оставшихся кандидатов и не должна отменять
эти ограничения.

### Использование вне назначения

Модель не предназначена для:

- медицинских рекомендаций и оценки безопасности употребления алкоголя;
- определения возраста или допуска пользователя к покупке;
- прогнозирования вкуса с гарантированной точностью;
- экспертной или объективной оценки качества вина;
- автономного принятия юридически значимых решений.

### Ограничения

1. **Холодный старт пользователя.** Без лайков персонализация невозможна.
2. **Холодный старт объекта.** Новое вино не попадёт в модель до переобучения.
3. **Только положительная обратная связь.** Дизлайки, покупки, просмотры и
   пропуски не учитываются.
4. **Узкий профиль.** Модель может предлагать однотипные вина и уменьшать
   разнообразие выдачи.
5. **Ручные веса.** Веса признаков и смешивания не оптимизированы на данных.
6. **Чувствительность нормализации цены.** Очень дорогой выброс изменяет масштаб
   цен для всего каталога.
7. **Пропуски.** Отсутствующий рейтинг трактуется как ноль; отсутствующие
   категории не добавляются в вектор.
8. **Состояние в памяти.** Модель теряется при перезапуске и автоматически не
   синхронизируется между несколькими экземплярами API.
9. **Нет подтверждённого качества.** Текущие тесты не доказывают эффективность
   на реальных пользователях.

### Компромиссы

- Content-based подход объясним и способен работать с небольшим числом
  взаимодействий, но не использует предпочтения похожих пользователей.
- Большой вес ML усиливает персонализацию, но может ухудшить разнообразие и
  влияние объективного рейтинга; меньший вес даёт более стабильную, но менее
  индивидуальную выдачу.
- Ручные категориальные веса упрощают разработку MVP, однако отражают
  предположения разработчиков и могут не соответствовать реальному поведению.
- Хранение в памяти обеспечивает быстрый инференс, но усложняет обновление,
  масштабирование и воспроизводимость модели.

### Этические риски и способы снижения

| Риск | Способ снижения |
|---|---|
| Стимулирование чрезмерного употребления алкоголя | Возрастная проверка, предупреждение об ответственном потреблении, отсутствие механик поощрения объёма потребления |
| Необоснованная персонализация | Объяснение причин рекомендации и возможность использовать неперсональную выдачу |
| Утечка истории предпочтений | Ограничение доступа, минимизация хранимых данных и соблюдение требований к приватности |
| «Пузырь фильтров» и однообразие | Метрики разнообразия, ограничение повторов и добавление исследовательских рекомендаций |
| Смещение из-за состава каталога | Анализ покрытия и качества по категориям, странам, брендам и ценовым сегментам |

### Рекомендации по развитию и мониторингу

- сформировать evaluation-набор с временным разделением данных;
- рассчитывать `NDCG@5`, `Precision@5`, `Recall@5` и coverage;
- логировать показы и реакции, проводить A/B-тест против standard ranking;
- подобрать веса признаков и коэффициент смешивания по данным;
- учитывать отрицательную обратную связь;
- добавить контроль разнообразия и новизны;
- сохранять версионированные артефакты модели во внешнем хранилище;
- мониторить долю режимов `ml`/`standard`, задержку, свежесть и drift данных.

## 5. Ответственность и воспроизводимость

Результат построения модели зависит от состояния каталога и таблицы лайков на
момент обучения. Endpoint переобучения возвращает время обучения, количество
вин, пользователей с профилем и учтённых лайков. Для полной воспроизводимости в
следующей версии необходимо сохранять снимок данных, конфигурацию весов, commit
SHA и сериализованный артефакт модели.
