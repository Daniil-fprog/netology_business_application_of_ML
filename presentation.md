# Презентация проекта Wine Recommendation Service

## Запуск перед презентацией

```bash
# Создать настройки, только если файла .env ещё нет
test -f .env || cp .env.example .env

# Собрать образы и запустить PostgreSQL и API в фоне
docker compose up --build -d

# Проверить состояние контейнеров
docker compose ps

# Проверить готовность API
curl http://localhost:8000/health
```

Ожидаемый ответ проверки:

```json
{"status":"ok"}
```

После запуска открыть:

- веб-интерфейс: <http://localhost:8000>;
- Swagger UI: <http://localhost:8000/docs>.

Контейнер автоматически применит миграции, загрузит mock-каталог и обучит
ML-модель. В демонстрационных данных находятся 100 вин, 20 пользователей и 120
лайков.

Если сервис уже был собран ранее, перед презентацией достаточно:

```bash
docker compose up -d
curl http://localhost:8000/health
```

Если API не запустился, посмотреть причину можно командой:

```bash
docker compose logs --tail=100 api
```

Ручное переобучение модели после изменения лайков:

```bash
curl -X POST http://localhost:8000/ml/retrain
```

Быстрая проверка рекомендации без браузера:

```bash
curl -X POST http://localhost:8000/recommendations \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1,"color":"red","sugar_type":"dry","max_price":1500,"min_rating":4,"limit":5}'
```

После презентации остановить сервис:

```bash
docker compose down
```

Данные PostgreSQL при этом сохранятся в Docker volume.

---

## Короткий план демонстрации

1. Открыть <http://localhost:8000> и показать фильтры.
2. Выбрать профиль пользователя, цвет, сахар, цену и рейтинг.
3. Получить рекомендации и показать карточки TOP-N.
4. Переключить профиль и повторить запрос, чтобы показать персонализацию.
5. Открыть <http://localhost:8000/docs> и показать endpoints.
6. Вызвать `POST /ml/retrain` и обратить внимание на количество вин,
   пользователей и лайков в ответе.
7. Завершить демонстрацию описанием текущих ограничений и следующих шагов.

## Рассказ о проекте

### Введение

Здравствуйте. Я представляю проект **Wine Recommendation Service** — это
MVP-сервис персонального подбора вина. Основная идея проекта состоит в том, чтобы
помочь пользователю быстро выбрать подходящее вино из каталога, не просматривая
вручную большое количество карточек товаров.

Пользователь задаёт простые требования:
- цвет вина
- содержание сахара
- диапазон цены
- минимальный рейтинг
- желаемое количество результатов.

Система преобразует эти параметры в SQL-запрос, который фильтрует каталог и формирует
ранжированный список рекомендаций. Если у пользователя уже есть история лайков,
выдача дополнительно персонализируется с помощью ML-модели.

Проект является учебным MVP, но в нём представлен полный путь данных: загрузка
каталога, хранение в базе, работа с пользователями и лайками, обучение модели,
получение рекомендаций через API и отображение результата в веб-интерфейсе.

### Проблема, цель и задачи

Проблема состоит в том, что обычные фильтры дают одинаковый результат всем
пользователям. Например, два человека могут запросить красное сухое вино до
1500 рублей, но одному нравятся итальянские вина из сорта Пино Гриджио, а другому
— вина другого региона и бренда. Одной сортировки по рейтингу недостаточно,
чтобы учесть эту разницу.

Цель проекта — сделать подбор одновременно понятным и персональным. Для этого
решаются несколько задач:

1. загрузить и нормализовать каталог вин;
2. сохранить товары, предложения, пользователей и лайки в базе данных;
3. принять и проверить параметры фильтрации;
4. отфильтровать неподходящие товары;
5. вычислить стандартный и персональный score;
6. вернуть TOP-N результатов через API и показать их в интерфейсе;
7. сохранить событие рекомендации для будущего анализа качества.

### Пользовательский сценарий

Пользователь открывает страницу сервиса и выбирает, например, красное сухое
вино стоимостью до 1500 рублей с рейтингом не ниже четырёх. Интерфейс напрямую
передаёт эти структурированные параметры и идентификатор выбранного профиля в API.

Pydantic проверяет допустимые значения и диапазоны, после чего repository добавляет
условия по цвету, содержанию сахара, цене и рейтингу в SQL-запрос. Поэтому модель
не может предложить белое или слишком дорогое вино, если пользователь явно указал
другие условия.

Далее возможны два режима. Для нового пользователя без лайков применяется
стандартное ранжирование. Для пользователя с обученным профилем включается
режим `ml`, и итоговый порядок учитывает сходство вин с его предпочтениями.
Уже понравившиеся товары исключаются, чтобы не показывать их повторно.

### Архитектура и технологии

Backend написан на **Python 3.11** и **FastAPI**. Uvicorn запускает HTTP-сервис,
а Pydantic проверяет входные и выходные схемы API. Для хранения используются
**PostgreSQL** и **SQLAlchemy**, а изменениями структуры базы управляет
**Alembic**.

Frontend сделан без тяжёлого фреймворка — это HTML, CSS и JavaScript. Он
позволяет выбрать фильтры, переключать пользовательские профили и увидеть
карточки рекомендованных вин.

Проект разделён на независимые слои. Модуль `parser` отвечает за загрузку и
нормализацию каталога. `recommendation` содержит схему фильтров, проверку
ограничений и формулы ranking. В `ml` находится персональная модель.
Модуль `db` изолирует работу с базой, а `api` связывает компоненты в единый
сценарий.

Приложение и PostgreSQL запускаются через **Docker Compose**. Для контроля
качества используются pytest, Ruff, mypy и pre-commit. Благодаря разделению
слоёв алгоритмы можно тестировать без запуска браузера и реальной базы.

### Данные проекта

Основная сущность — вино. Для него хранятся название, бренд, страна, регион,
цвет, тип сахара, сорт винограда, изображение и ссылка. Отдельно хранится
предложение магазина: цена, рейтинг, число отзывов и наличие. Такое разделение
позволяет в будущем подключить несколько магазинов к одному товару.

Также в базе есть пользователи, их лайки и история событий рекомендаций. Для
демонстрации используется локальный JSON-набор: 100 вин, 20 пользователей и 120
лайков. Он загружается автоматически и не требует обращения к внешнему сайту.

### Как работает ML-модель

В проекте используется самописная **content-based рекомендательная модель**.
Это не нейросеть и не готовая модель из scikit-learn. Её задача — оценить,
насколько конкретное вино похоже на то, что уже нравилось пользователю.

Сначала каждое вино преобразуется в вектор признаков. В него входят цена,
рейтинг, цвет, тип сахара, страна, бренд и сорта винограда. Числовые признаки
масштабируются: рейтинг делится на пять, а цена — на максимальную цену в
каталоге. Категориальным признакам назначены веса. Самый большой вес, равный
двум, имеют цвет и тип сахара. Вес винограда — полтора, страны — один, бренда —
ноль целых семьдесят пять сотых. После этого вектор нормализуется.

Профиль пользователя строится как среднее значение векторов всех вин, которым
он поставил лайк. Полученный профиль также нормализуется. Сходство кандидата с
профилем рассчитывается как скалярное произведение нормализованных векторов, то
есть фактически как косинусная близость. Чем ближе score к единице, тем сильнее
вино соответствует накопленным предпочтениям.

ML-score не используется изолированно. Он смешивается со стандартной оценкой:

```text
final_score = 0.35 * standard_score + 0.65 * ml_score
```

Стандартная оценка на 55 процентов зависит от рейтинга, на 25 процентов — от
соответствия цене и на 20 процентов — от популярности по числу отзывов. Также
может применяться небольшой бонус за любимое сочетание цвета и сахара. Все эти
веса вынесены в настройки.

Так получается гибридная схема: бизнес-фильтры гарантируют соответствие выбранным
параметрам, стандартный ranking сохраняет влияние качества и популярности, а
content-based модель добавляет персонализацию.

### Обучение и переобучение

При запуске Docker-контейнера сначала применяются миграции, затем загружаются
mock-данные, после чего модель автоматически строит векторы каталога и профили
пользователей. Также доступен endpoint `POST /ml/retrain`, который повторно
строит модель по текущему каталогу и лайкам.

Текущая версия хранит модель в оперативной памяти процесса API. Поэтому после
новых лайков требуется переобучение, а при нескольких экземплярах API модель
нужно синхронизировать. Для дальнейшего развития подготовлена схема
автоматического MLOps-процесса: триггер по расписанию или новым данным,
валидация данных, обучение candidate-версии, quality gate, регистрация версии,
staging, canary-деплой, мониторинг и rollback при ухудшении качества.

### Тестирование и метрики

На момент подготовки презентации полный набор автоматических тестов проекта
содержит **24 успешно пройденных теста**. Они проверяют валидацию параметров,
жёсткую фильтрацию и сортировку, расчёт персонального сходства, исключение уже
понравившихся вин, fallback для пользователя без лайков, repository, загрузку
mock-каталога и основные API-сценарии.

В текущем MVP ещё нет отдельной временной test-выборки, поэтому значения
`NDCG@5`, `Precision@5`, `Recall@5` и `HitRate@5` пока не измерены. Основной
offline-метрикой для следующей версии предлагается `NDCG@5`, потому что она
учитывает не только наличие релевантных товаров, но и их порядок в TOP-5.
Дополнительно нужно измерять покрытие каталога, долю пользователей с доступной
персонализацией и online-метрики — CTR и конверсию в лайк. Итоговый эффект нужно
проверять A/B-тестом против стандартного ranking.

### Ограничения и итог

Главное ограничение — холодный старт: без лайков модель не знает предпочтения
пользователя и переключается на стандартную выдачу. Модель учитывает только
положительную обратную связь и пока не использует покупки, просмотры или
дизлайки. Ручные веса не подбирались на реальной истории. Кроме того,
content-based подход может создавать слишком однообразную выдачу.

В дальнейшей работе можно добавить временную offline-оценку, автоматический
подбор весов, отрицательную обратную связь, контроль разнообразия,
версионирование модели и безопасный автоматический деплой. Так как проект связан
с алкогольной продукцией, в реальном сервисе также необходимы возрастные
ограничения и ответственная подача рекомендаций.

В результате получился работающий MVP, который объединяет веб-интерфейс, API,
базу данных, загрузку каталога и объяснимую персональную модель. Его ключевое
преимущество — прозрачность: можно показать, из каких данных формируется
профиль, как рассчитывается score и почему конкретное вино поднялось в выдаче.
