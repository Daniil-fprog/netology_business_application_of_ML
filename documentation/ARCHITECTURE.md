# Структура Wine Recommendation Service

Документ объясняет устройство проекта, ответственность каталогов и модулей, а также движение данных между ними.

## Общая схема

Приложение разделено на несколько слоёв:

```text
HTML/JavaScript или другой API-клиент
                    │
                    ▼
              FastAPI routes
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
    Query Parser      Parser Service
          │                   │
          ▼                   ▼
 Recommendation       WineSource adapter
    Service                   │
          │                   ▼
          └────────► Repository ◄────────┐
                         │               │
                         ▼               │
                 SQLAlchemy models       │
                         │               │
                         ▼               │
                     PostgreSQL ─────────┘
```

Основная идея разделения: HTTP-слой отвечает только за приём и выдачу данных, бизнес-правила находятся в отдельных сервисах, а работа с базой данных сосредоточена в repository. Благодаря этому рекомендательный алгоритм и разбор текста можно тестировать без запуска API и PostgreSQL.

## Корневые файлы

### `pyproject.toml`

Главный конфигурационный файл Python-проекта. Он содержит:

- название и версию приложения;
- production-зависимости: FastAPI, Uvicorn, SQLAlchemy, Alembic, Psycopg и Pydantic;
- dev-зависимости: pytest, Ruff, mypy и pre-commit;
- настройки тестов, линтера, форматтера и проверки типов;
- указание, что Python-пакет находится в каталоге `src`.

### `poetry.lock`

Фиксирует точные версии прямых и транзитивных зависимостей. Благодаря lock-файлу локальная среда, CI и Docker устанавливают одинаковые библиотеки.

### `.env.example`

Шаблон переменных окружения. В нём находятся:

- `DATABASE_URL` — строка подключения к PostgreSQL;
- `LOG_LEVEL` — уровень логирования;
- `PARSER_*` — параметры загрузки каталога;
- `RANKING_*` — веса формулы ранжирования.

Рабочая копия называется `.env` и не добавляется в Git.

### `Dockerfile`

Описывает сборку контейнера API. Образ устанавливает Poetry и production-зависимости, копирует исходный код и запускает Uvicorn.

### `docker-compose.yml`

Объединяет два сервиса:

- `db` — PostgreSQL 16 с постоянным Docker volume;
- `api` — FastAPI-приложение.

Перед запуском API Compose ждёт успешный healthcheck PostgreSQL. Затем API применяет миграции и запускает веб-сервер.

### `.pre-commit-config.yaml`

Настраивает автоматические проверки перед Git-коммитом:

- удаление лишних пробелов;
- проверку окончания файлов;
- проверку YAML и TOML;
- Ruff linting и форматирование;
- mypy;
- pytest.

### `README.md`, `RUN.md`, `technical.md`, `tz.md`

- `README.md` — краткое описание, архитектура и быстрый старт;
- `RUN.md` — команды запуска и обслуживания с пояснениями;
- `technical.md` и `tz.md` — постановка задачи и исходные требования проекта.

## Пакет `src/wine_recommendation`

Это основной Python-пакет приложения. Использование `src`-структуры не позволяет случайно импортировать код непосредственно из корня репозитория и приближает локальную среду к установленному пакету.

### `main.py`

Точка входа приложения. Модуль:

- создаёт объект `FastAPI`;
- подключает группы маршрутов;
- публикует статические файлы по адресу `/static`;
- возвращает главную HTML-страницу по адресу `/`;
- логирует запуск и остановку приложения;
- преобразует доменные исключения в HTTP-ответы 404, 409, 422 и 502.

Uvicorn загружает приложение по пути `wine_recommendation.main:app`.

### `__init__.py`

Обозначает каталог как Python-пакет. В некоторых подпакетах такие файлы также экспортируют основные классы, чтобы импорты были короче.

## Модуль `core`

Содержит общие инфраструктурные настройки, которые используются несколькими частями приложения.

### `core/config.py`

Читает переменные окружения и создаёт неизменяемый объект `settings`. В нём хранятся параметры БД, логирования, парсера и ranking. Бизнес-код получает значения из конфигурации и не содержит environment-specific настроек напрямую.

### `core/logging.py`

Настраивает стандартный Python `logging`: уровень сообщений и единый формат. Рабочий код использует logger вместо `print()`.

## Модуль `api`

HTTP-слой приложения. Он проверяет входные данные, вызывает сервисы и repository, а затем формирует JSON-ответы.

### `api/dependencies.py`

Описывает FastAPI dependency injection:

1. `get_session()` создаёт SQLAlchemy-сессию;
2. `get_repository()` оборачивает её в `Repository`;
3. routes получают готовый `RepositoryDep` как аргумент функции.

После завершения запроса сессия закрывается автоматически.

### `api/schemas.py`

Содержит Pydantic-схемы HTTP-запросов и ответов:

- создание и чтение пользователя;
- добавление и чтение лайка;
- представление вина и предложения магазина;
- запрос рекомендаций;
- карточка рекомендации;
- результат обновления парсера.

Pydantic проверяет обязательные поля, длину строк и допустимые диапазоны чисел до передачи данных бизнес-логике.

### `api/routes/system.py`

Системные endpoints:

- `GET /health` — подтверждает, что API работает;
- `POST /parser/update` — запускает обновление каталога.

Парсер нельзя запустить, пока `PARSER_ENABLED` не установлен в `true`. Это защищает от случайного обращения к внешнему источнику до проверки условий его использования.

### `api/routes/wines.py`

Маршруты каталога и пользовательских действий:

- получение списка вин;
- получение одного вина;
- создание пользователя;
- добавление лайка;
- удаление лайка.

Route-функции не выполняют SQL самостоятельно, а делегируют работу repository.

### `api/routes/recommendations.py`

Оркестрирует полный сценарий рекомендации:

1. принимает исходный текст и лимит;
2. разбирает текст через `RuleBasedQueryParser`;
3. при наличии пользователя получает его предпочтения из лайков;
4. получает доступные вина из repository;
5. запускает `RecommendationService`;
6. сохраняет событие рекомендации;
7. возвращает разобранные фильтры и карточки вин.

## Модуль `db`

Отвечает за структуру данных и взаимодействие с PostgreSQL.

### `db/session.py`

Создаёт SQLAlchemy engine и фабрику сессий `SessionLocal`. Функция `get_session()` используется FastAPI и гарантирует закрытие сессии после HTTP-запроса.

### `db/models/base.py`

Содержит:

- `Base` — базовый класс всех SQLAlchemy-моделей;
- `TimestampMixin` — повторно используемые поля `created_at` и `updated_at`.

### `db/models/entities.py`

Описывает таблицы базы данных:

- `User` — пользователь с внешним идентификатором и именем;
- `Wine` — постоянные характеристики вина;
- `WineOffer` — цена, рейтинг, наличие и ссылка конкретного магазина;
- `UserLike` — связь many-to-many между пользователями и винами;
- `RecommendationEvent` — история запросов, распознанных параметров и выданных вин.

Разделение `Wine` и `WineOffer` позволяет в будущем прикрепить к одному вину предложения нескольких магазинов.

### `db/repositories/repository.py`

Единая точка доступа к данным. Класс `Repository`:

- создаёт и получает пользователей;
- читает каталог;
- добавляет и удаляет лайки;
- преобразует записи БД в `WineCandidate`;
- определяет наиболее частую пару `color + sugar_type` среди лайков;
- сохраняет историю рекомендаций;
- выполняет upsert вин и предложений после парсинга;
- помечает исчезнувшие предложения недоступными.

Исключения `NotFoundError` и `ConflictError` позволяют сообщать API о предсказуемых ошибках без привязки repository к HTTP-кодам.

## Модуль `query_parser`

Преобразует пользовательскую строку в структурированные фильтры без LLM и внешних NLP-моделей.

### `query_parser/schemas.py`

Содержит:

- `Color` — допустимые цвета вина;
- `SugarType` — допустимые типы по содержанию сахара;
- `WineQuery` — итоговые фильтры: цвет, сахар, минимальная и максимальная цена, минимальный рейтинг.

Схема проверяет диапазоны значений и запрещает минимальную цену выше максимальной.

### `query_parser/parser.py`

Содержит интерфейс `QueryParser` и реализацию `RuleBasedQueryParser`. Parser:

- приводит текст к единому регистру;
- ищет цвет и содержание сахара в ограниченном словаре;
- регулярными выражениями распознаёт `до 1500`, `от 1000` и `от 1000 до 2000`;
- распознаёт конструкции рейтинга;
- возвращает `WineQuery`;
- создаёт `QueryParseError` для некорректного ввода.

Интерфейс позволяет позднее заменить rule-based реализацию на NLP или LLM без изменения рекомендательного сервиса.

## Модуль `recommendation`

Содержит независимую от FastAPI и SQLAlchemy бизнес-логику рекомендаций.

### `recommendation/schemas.py`

- `WineCandidate` — входная карточка вина для алгоритма;
- `WineRecommendation` — результат с рассчитанным `score`.

Обе структуры реализованы как неизменяемые dataclass-объекты.

### `recommendation/ranking.py`

Выполняет расчёт score. `RankingWeights` хранит веса рейтинга, цены, популярности и персонального бонуса. Функция `calculate_score()` объединяет:

- нормализованный рейтинг `rating / 5`;
- соответствие цены запросу;
- логарифмически нормализованное количество отзывов;
- небольшой бонус за совпадение с предпочтениями пользователя.

Отдельная функция `_price_score()` по-разному оценивает цену для верхней границы, нижней границы и диапазона.

### `recommendation/service.py`

`RecommendationService` выполняет два этапа:

1. фильтрует вина по цвету, сахару, цене и рейтингу;
2. рассчитывает score, сортирует результаты и оставляет TOP-N.

При равном score используется стабильная сортировка по идентификатору вина.

## Модуль `parser`

Получает каталог из внешнего источника, нормализует данные и передаёт их repository.

### `parser/base.py`

Определяет протокол `WineSource`. Любой новый источник должен иметь имя и метод `fetch()`, возвращающий список `ParsedWine`. Здесь же находится общее исключение `SourceError`.

### `parser/schemas.py`

`ParsedWine` — промежуточная нормализованная модель товара. Она содержит характеристики вина и данные предложения магазина. Методы `wine_values()` и `offer_values()` разделяют объект на значения для таблиц `Wine` и `WineOffer`.

### `parser/perekrestok.py`

Адаптер каталога Перекрёстка. Он:

- отправляет HTTP-запрос с заданным User-Agent и timeout;
- обрабатывает сетевые ошибки и некорректный JSON;
- принимает массив или объект с полем `items`/`products`;
- пропускает отдельные повреждённые записи, не останавливая весь импорт;
- нормализует цвет и содержание сахара;
- корректно обрабатывает отсутствующие необязательные поля.

Endpoint не зашит в исходный код и передаётся через `PEREKRESTOK_API_URL`, поскольку адрес и правила использования источника могут меняться.

### `parser/service.py`

`ParserService` соединяет источник с repository:

```text
WineSource.fetch() -> list[ParsedWine] -> Repository.upsert_wines()
```

Сервис также логирует начало, завершение и количество обработанных товаров.

## Модуль `static`

Простой frontend без отдельного JavaScript-фреймворка.

### `static/index.html`

Содержит форму фильтров слева и область рекомендаций справа. Пользователь может выбрать цвет, содержание сахара, диапазон цены, рейтинг и количество результатов.

### `static/styles.css`

Отвечает за двухколоночную раскладку, прокрутку списка, карточки вин, состояния загрузки и мобильную адаптацию. На узком экране форма и результаты располагаются друг под другом.

### `static/app.js`

Frontend-логика:

1. читает значения формы;
2. формирует русскоязычную строку запроса;
3. вызывает `POST /recommendations` через `fetch`;
4. показывает skeleton во время ожидания;
5. создаёт карточки из JSON-ответа;
6. показывает пустое состояние или сообщение об ошибке;
7. проверяет и экранирует полученные строки и ссылки.

## Каталог `alembic`

Alembic управляет версионными изменениями схемы БД.

### `alembic.ini`

Основная конфигурация Alembic: расположение миграций и настройки логирования.

### `alembic/env.py`

Подключает SQLAlchemy metadata и значение `DATABASE_URL`. Поддерживает online-режим с подключением к БД и offline-режим генерации SQL.

### `alembic/versions/0001_initial.py`

Начальная миграция. Функция `upgrade()` создаёт все таблицы, ограничения и индексы. Функция `downgrade()` удаляет их в обратном порядке.

### `alembic/script.py.mako`

Шаблон, по которому Alembic создаёт новые файлы миграций.

## Каталог `scripts`

### `scripts/update_parser.py`

CLI-точка запуска обновления каталога. Скрипт проверяет, разрешён ли парсер, создаёт `PerekrestokSource`, открывает сессию БД и запускает `ParserService`.

## Каталог `tests`

Тесты разделены по уровню.

### `tests/unit`

- `test_query_parser.py` проверяет словарь, цены, рейтинг и ошибочные запросы;
- `test_recommendation.py` проверяет фильтрацию, ranking, TOP-N и персональный бонус;
- `test_source.py` проверяет нормализацию сохранённого ответа источника без обращения к реальному сайту.

Unit-тесты фокусируются на одном модуле и не требуют PostgreSQL.

### `tests/integration`

- `test_repository.py` проверяет SQLAlchemy upsert и смену доступности предложения;
- `test_api.py` проверяет health endpoint, публикацию frontend и полный сценарий рекомендации через HTTP.

Для изоляции integration-тесты используют временную SQLite-базу.

### `tests/fixtures`

`perekrestok.json` — сохранённый тестовый ответ источника. Он позволяет тестировать parser детерминированно, быстро и без сетевых запросов.

## Сценарий формирования рекомендации

Запрос `красное сухое до 1500` проходит следующие шаги:

1. `app.js` отправляет `POST /recommendations`.
2. Pydantic проверяет тело запроса.
3. `RuleBasedQueryParser` создаёт `WineQuery(color="red", sugar_type="dry", max_price=1500)`.
4. Repository выбирает доступные `WineOffer` и преобразует их в `WineCandidate`.
5. При указанном пользователе repository анализирует его лайки.
6. `RecommendationService` удаляет неподходящие вина.
7. Ranking рассчитывает score оставшихся кандидатов.
8. Сервис сортирует результаты и оставляет заданное количество.
9. Repository сохраняет `RecommendationEvent`.
10. API возвращает JSON, а `app.js` отображает карточки.

## Сценарий обновления каталога

1. Администратор вызывает `POST /parser/update` или CLI-скрипт.
2. Проверяется флаг `PARSER_ENABLED`.
3. `PerekrestokSource` получает JSON и преобразует записи в `ParsedWine`.
4. `ParserService` передаёт данные в repository.
5. Для уже существующих записей обновляются характеристики и предложение.
6. Новые записи добавляются.
7. Предложения, отсутствующие в успешном полном снимке источника, получают `is_available=false`.
8. Транзакция фиксируется в PostgreSQL.

## Как расширять проект

### Добавить новый магазин

Нужно реализовать новый класс протокола `WineSource`, например `WineLabSource`, который возвращает `list[ParsedWine]`. Recommendation и query parser изменять не потребуется.

### Заменить разбор текста

Новая реализация должна соответствовать протоколу `QueryParser` и возвращать `WineQuery`. Остальная бизнес-логика продолжит работать с тем же контрактом.

### Изменить алгоритм ranking

Можно изменить `calculate_score()` или добавить другую стратегию внутри `recommendation`, не меняя HTTP API и parser источника.

### Добавить новый endpoint

Нужно создать или дополнить модуль в `api/routes`, описать Pydantic-схемы и подключить router в `main.py`.
