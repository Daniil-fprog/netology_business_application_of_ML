# Техническое задание
## Wine Recommendation Service — MVP

### 1. Цель проекта

Разработать MVP рекомендательной системы для подбора вина пользователю.

Пользователь должен иметь возможность выбрать в форме цвет вина, содержание
сахара, диапазон цены, минимальный рейтинг и количество результатов.

Интерфейс передаёт выбранные значения в API как отдельные структурированные поля.
Система валидирует их, применяет жёсткие SQL-фильтры и возвращает несколько
наиболее подходящих вин из базы данных.

---

# 2. Основной функционал MVP

Система должна включать следующие компоненты:

1. сбор данных о винах;
2. хранение данных;
3. хранение пользователей и их действий;
4. валидация структурированных параметров пользователя;
5. фильтрация вин;
6. рекомендательный алгоритм;
7. API для работы с системой;
8. тесты;
9. инструменты контроля качества кода.

---

# 3. Источник данных

Первоначальный источник данных — каталог «Перекрёстка».

Необходимо реализовать отдельный модуль `parser`, отвечающий за получение и преобразование информации о винах.

Для каждого вина по возможности получать:

- название;
- производитель/бренд;
- страна;
- регион;
- цвет;
- содержание сахара / тип: сухое, полусухое, полусладкое, сладкое;
- сорт винограда;
- цена;
- старая цена/скидка, если доступны;
- объём;
- рейтинг;
- количество оценок;
- URL товара;
- URL изображения;
- описание;
- дата последнего обновления.

Парсер не должен быть связан напрямую с рекомендательным алгоритмом.

Предусмотреть интерфейс источника данных, чтобы в дальнейшем можно было добавить другие магазины без изменения основной бизнес-логики.

Например:

`WineSource -> MockJsonSource`

В дальнейшем:

`WineSource -> WineLabSource`

`WineSource -> OtherSource`

Парсер должен корректно обрабатывать отсутствие отдельных полей, сетевые ошибки, изменение доступности товара и повторное появление уже существующего вина.

Перед эксплуатацией парсера необходимо проверить допустимость автоматизированного получения и использования данных конкретного источника.

# 5. Параметры фильтрации

API принимает параметры напрямую, без построения и разбора текстовой строки:

```python
WineFilters(
    color="red",
    sugar_type="dry",
    min_price=None,
    max_price=1500,
    min_rating=4,
)
```

Допустимые цвета: `red`, `white`, `rose`.

Допустимые типы по содержанию сахара: `dry`, `semi_dry`, `semi_sweet`, `sweet`.

Минимальная и максимальная цена должны быть неотрицательными, минимальная цена
не может превышать максимальную. Рейтинг задаётся числом от 0 до 5.

Параметры добавляются в SQL `WHERE`. Если параметр не передан, соответствующее
ограничение не применяется.

# 6. Первая версия рекомендательного алгоритма

На первом этапе не использовать Collaborative Filtering и сложные ML-модели.

Алгоритм должен состоять из двух этапов.

### Этап 1. Фильтрация

На основании `WineFilters` выбрать вина, соответствующие ограничениям пользователя.

Например:

`color = red`

`AND sugar_type = dry`

`AND price <= 1500`

### Этап 2. Ranking

Оставшиеся вина ранжировать.

Базовый score:

```text
score =
    w1 × normalized_rating
    + w2 × price_score
    + w3 × popularity_score
```

Где:

- `normalized_rating` — нормализованный рейтинг вина;
- `price_score` — соответствие цены выбранному диапазону;
- `popularity_score` — показатель на основе количества оценок/лайков.

Коэффициенты `w1`, `w2`, `w3` должны храниться в конфигурации и легко изменяться.

Алгоритм должен возвращать, например, TOP-5 вин.

Для каждого результата вернуть:

- название;
- цену;
- рейтинг;
- характеристики;
- изображение;
- ссылку на источник;
- итоговый `score`.

# 7. Использование лайков

В первой версии лайки преимущественно собираются для будущего обучения рекомендательной системы.

Дополнительно можно реализовать простую персонализацию.

Например, если пользователь чаще ставит лайк:

`red + dry`

такие вина получают небольшой дополнительный коэффициент при ранжировании.

Однако отсутствие лайков не должно мешать работе системы.

Таким образом решается проблема cold start: новый пользователь получает рекомендации по рейтингу, цене и выбранным параметрам.

# 8. API

Для backend использовать Python + FastAPI.

Минимальные endpoints:

```text
GET /health

GET /wines
GET /wines/{id}

POST /users

POST /users/{id}/likes
DELETE /users/{id}/likes/{wine_id}

POST /recommendations

POST /parser/update
```

Пример запроса:

```json
{
    "user_id": 15,
    "color": "red",
    "sugar_type": "dry",
    "max_price": 1500,
    "min_rating": 4,
    "limit": 5
}
```

Пример ответа:

```json
{
    "applied_filters": {
        "color": "red",
        "sugar_type": "dry",
        "max_price": 1500,
        "min_rating": 4
    },
    "recommendation_mode": "standard",
    "recommendations": []
}
```

# 20. Критерии готовности MVP

Проект считается выполненным, если:

1. данные о винах можно получить из выбранного источника и сохранить в PostgreSQL;
2. повторный запуск parser корректно обновляет существующие данные;
3. существуют модели пользователей, вин, предложений, лайков и рекомендаций;
4. интерфейс передаёт параметры формы в API отдельными полями;
5. система применяет к каталогу жёсткую SQL-фильтрацию по полученным параметрам;
6. рассчитывается ranking score;
7. возвращается TOP-N рекомендаций;
8. пользователь может поставить/убрать лайк;
9. история рекомендаций сохраняется;
10. приложение имеет FastAPI API;
11. схема БД управляется Alembic;
12. зависимости управляются Poetry;
13. `poetry.lock` находится в Git;
14. `.venv` и `.env` не находятся в Git;
15. настроен pre-commit;
16. проходят Ruff, mypy и pytest;
17. приложение запускается через Docker Compose;
18. проект содержит инструкцию запуска в README.

# 21. Что не входит в MVP

На первом этапе намеренно не реализовывать:

- LLM;
- embeddings;
- semantic search;
- нейронные сети;
- Collaborative Filtering;
- сложный Content-Based ML;
- обучение модели на пользовательских данных;
- мобильное приложение;
- сложную персонализацию.

Архитектура должна позволять добавить эти компоненты позднее без полной переработки проекта.

Главная задача MVP — проверить полный цикл:

**данные → параметры пользователя → SQL-фильтрация → ranking → рекомендация → feedback пользователя.**
